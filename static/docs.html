What it is

DocsForge turns a documentation site into clean Markdown a language model can actually read — so a model that was never trained on your stack can still answer questions about it.

Give it a URL in the chat. It works out what kind of source that URL is, extracts it, and answers from what it fetched rather than from memory. Every answer can be copied, edited in place, or downloaded as a .md file you keep.

What it can read

SourceWhat happens
llms.txtThe LLM-native docs standard, passed straight through.
openapiSwagger or OpenAPI, JSON or YAML, rendered as endpoint tables.
sitemapEvery page listed in a sitemap.xml, indexes included.
githubA repository's README plus everything under docs/.
htmlA normal docs site, with nav, footers and chrome stripped out.
raw_textMarkdown or plain text, cleaned up.

You do not have to say which one it is. Detection is one cheap probe, and the answer shows what it decided.

Learning a whole library

Fetching one page answers a question about that page. Learning a whole library is a different job, and it has its own tool: harvest. Ask for "the whole documentation" of something and it starts from any page and finds the rest, best strategy first:

  1. llms.txt or llms-full.txt — the site already published itself for machines.
  2. sitemap.xml, filtered to the docs section. Complete, cheap, and it finds pages nothing links to.
  3. A scoped crawl. Works anywhere, but only reaches what is linked.

It stays inside the documentation

Docs share a domain with marketing, blogs and changelogs. Crawling by host from an Effect docs page reached /podcast within four pages, and that page then dominated what the model saw — so it summarised a podcast feed instead of the library. Harvesting stays inside the documentation root of the URL you gave it: /docs/v3/getting-started/introduction/ becomes /docs/v3/.

There is no page limit

A harvest runs until the documentation section is exhausted. A page count is only ever a guess at how big someone else's manual is; the Effect v3 docs come to 703 pages and nothing knew that in advance. If you do set a limit and it is hit, every later read says so:

INCOMPLETE — stopped at the 200-page limit, 400+ pages still queued.

That matters more than the limit itself. A third of a manual that looks whole produces confident, wrong answers.

Versions

A library's v2 and v3 docs contradict each other, and a model handed both will quote the wrong one. So a harvest is filed under a version, not just a name, and re-harvesting one version leaves the others alone.

pydantic
  2.11   85 pages   1.2 MB
  1.10   24 pages   198 KB

The label comes from the URL — /docs/v3/, /docs/validation/2.11/ — and is then checked against what came back. A site publishes one llms.txt for its current release, so if that is what got served instead of the version you asked for, the label falls back to the harvest date rather than claiming a precision the content does not have. Sites that publish one version at a time are always dated: the date says which snapshot this is.

DocsStore

DocsStore is everything harvested so far, three levels deep: a technology, every crawled version of it, and the pages of the version you open. The list is paged because it grows every time anyone harvests. Inside a version, search runs over that version only and marks what matched.

Every view is addressable, so a link goes exactly where you meant: /library#/effect/v3/41.

The tools

These are what the model can call. The same six are exposed over MCP, so an editor gets identical behaviour.

ToolWhat it does
fetch_docsExtract one URL as Markdown. The everyday one.
harvest_docsLearn a whole technology from one URL and store it.
read_knowledge_baseRead stored docs back, optionally only the pages matching a phrase.
list_knowledge_baseWhat has been harvested, and which versions of each.
save_docsWrite extracted docs to files on disk.
detect_source_typeIdentify a URL without extracting it.

Every call a model makes is listed above the answer it produced, with what it fetched and how much came back. An answer that quietly came from nowhere looks different from one that did not.

Where it all lives

Two backends, chosen automatically.

WhenWhat you get
Markdown filesthe default knowledge_base/<tech>/<version>.md. Zero setup, and the file is a deliverable you can hand to anyone.
PostgreSQLDOCSFORGE_DB is set and reachable A row per page with a full-text index. Search is ranked and stays fast as the store grows.
 
DOCSFORGE_DB=postgresql://postgres:password@127.0.0.1:5432/DocsForge

The schema is created on first use. If the database is unreachable it falls back to files rather than losing a harvest — losing ten minutes of crawling to a database outage would be the worse failure. DocsStore names which backend answered, because one ranks search and the other cannot.

Using it from an editor

The same six tools are served over MCP, so Claude Code or any MCP client can use them directly:

python mcp_server.py            # stdio
python mcp_server.py --http     # HTTP

The web chat and an MCP client run the same code path, so they behave identically.
